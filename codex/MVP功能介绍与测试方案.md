# AI 日程助手 MVP：功能介绍与测试方案

适用对象：小组成员、体验同学、项目展示评审。

本方案用于接下来的测试，不是新的测试通过证明。已有执行结果见《MVP验收报告.md》；本次编写方案没有重新运行测试。

## 一、我们的产品能做什么

我们的产品帮助学生处理“课程固定、任务很多、截止时间不同、临时事情不断增加”的情况。

用户已有基础课表，通过聊天告诉助手新增任务、截止时间、需要多久，以及希望什么时候做。AI理解这些要求，排程程序结合已有任务安排出候选方案，展示哪些任务发生了变化。用户可以继续修改，确认满意后再保存。

核心流程：**输入任务 → 理解要求 → 检查冲突与DDL → 预览调整 → 继续修改 → 确认保存。**

DDL就是任务的截止时间。

| 功能 | 用户可以做什么 | 我们需要验证什么 |
|---|---|---|
| 基础课表 | 查看已经导入的课程 | 课程时间准确，安排任务时不会覆盖课程 |
| 聊天添加任务 | 输入名称、时长、DDL、重要程度和时间要求 | AI理解正确；缺信息先问，不擅自猜 |
| 任务记忆 | 查看和修改已有任务及DDL | 刷新后资料保留，下一次安排仍考虑已有任务 |
| 多任务调整 | 插入紧急任务，或改变已有任务时间 | 不只安排新任务，还能调整已有任务并检查截止时间 |
| 冲突处理 | 指定与课程冲突的时间，查看备选 | 说明冲突对象，不能生成覆盖课程的可采用方案 |
| 变化解释 | 查看新增、移动和移除的任务 | 前后时间、原因与真实安排一致 |
| 确认与放弃 | 采用满意的方案，或放弃本轮 | 确认前不改正式计划；放弃后正式数据保持原样 |
| 锁定与进度管理 | 锁定安排、标记完成或取消 | 锁定和已开始任务不能静默移动，历史保留 |

这一版只调整当前周，任务连续安排、不自动拆分；不包含跨周规划、提醒、教务登录或外部日历同步。“记住任务”依靠保存的任务资料，不是模型长期记忆。

## 二、测试想回答的三个问题

1. **安排是否正确？** 有没有覆盖课程、任务重叠、排到过去或错过DDL？
2. **调整是否有帮助？** 临时任务出现后，能否梳理已有任务，并清楚说明变化？
3. **用户是否能放心操作？** 未确认、放弃、刷新、重复点击或AI失败，会不会误改数据？

不能只看AI回答是否自然，必须同时检查右侧日程和任务资料。

## 三、测试前准备

### 1. 使用独立演示环境

在项目目录打开PowerShell：

```powershell
& .\codex\启动演示版.ps1 -Reset -AiModel 'glm-5.3-flash'
```

打开 http://localhost:5174。该模型需要在本人的网关账户可用；密钥保存在本地backend/.env，不填入测试记录。

演示固定为2026-10-05至10-11这一周，模拟现在是**10月7日周三18:00，北京时间**。测试里“明天”指10月8日，不是电脑实际日期的次日。页面应持续显示演示模式。

Reset只重置演示环境，新建演示数据库并保留旧库。各独立场景重新Reset；下面的连续主流程中途不要Reset。

本机使用个人基础课表，公共项目默认使用匿名课程样例。个人课表有两项待补充，测试不能把它们当作已核实课程。

### 2. 核对初始任务

| 任务 | 所需时长 | 重要程度 | DDL | 初始安排 |
|---|---|---|---|---|
| 云计算作业 | 90分钟 | 普通 | 10月8日20:00 | 10月8日16:00–17:30 |
| 软件工程报告 | 120分钟 | 高 | 10月11日20:00 | 10月7日19:00–21:00 |
| 文献阅读 | 60分钟 | 低 | 10月11日22:00 | 10月8日10:30–11:30 |

每天12:00–14:00、18:00–19:00、21:00–22:00为演示用保护时间，不代表所有学生的真实习惯。

## 四、先跑一条完整主流程

这一条最能展示产品核心。建议由一名同学操作，另一名同学记录结果。

| 步骤 | 操作或聊天输入 | 应观察到的结果 |
|---|---|---|
| 1 查看基础数据 | 打开日程，展开任务记忆 | 能看见课程、三项任务、各自DDL和演示日期 |
| 2 正常新增 | “周五20:00前交实验报告，预计两小时，尽量周四下午做。” | 名称、120分钟、10月9日20:00截止理解正确；生成候选。若偏好无法满足，应明确提示。正式任务仍是三项 |
| 3 制造课程冲突 | “实验报告改到周四14:00。” | 指出与云计算课程冲突；没有覆盖课程的可采用方案；能够给出改变时间要求后的备选 |
| 4 改变要求 | “那把实验报告放在周四19:00。” | 更新同一项草稿，不重复新增；生成符合新要求的候选 |
| 5 插入紧急任务 | “明天中午12:00前还要交汇报稿，预计一小时，很重要。” | 正确记录60分钟、高重要程度、10月8日12:00截止；结合已有任务调整，检查文献阅读等任务是否移动及是否仍满足DDL |
| 6 再次调整两项任务 | “实验报告改到今晚19:00，汇报稿明早做。” | 同时修改两项任务；软件工程报告等已有任务可随之移动；没有遗漏任务、修改无关DDL或重复新增 |
| 7 查看原因并保存 | 点击AI解释，核对后点击采用；刷新页面 | 解释对应真实变化；正式任务为五项；日程和DDL保留；原三项任务DDL不变 |

模型提出必要问题时，按问题补充回答。例如：“汇报稿安排在10月8日10:30开始，时长和DDL不变。”记录补充回答和重试次数，不把人工补充后的成功写成一次输入成功。

通过标准是所有安排满足约束、变化可理解、确认后保存。不要求其他可移动任务必须落在唯一指定时段。

## 五、再测试独立场景

优先级P0表示必须通过；P1表示应在展示前检查。AI或网络故障可以给出失败说明，**清楚失败并保护数据也可以通过该异常测试**。

| 编号 | 优先级 | 场景与操作 | 通过标准 |
|---|---|---|---|
| T01 | P0 | 输入“新增一个阅读总结任务”，再补充“30分钟，周日20:00截止” | 先追问时长和具体DDL；补充后修改同一草稿，不重复新增 |
| T02 | P0 | 输入“周五晚上截止”，未说明钟点 | 确认具体截止钟点，不擅自当作20:00或22:00 |
| T03 | P0 | 建立两个同名任务，再只用名称要求改期 | 让用户选择目标，不猜测要修改哪一项 |
| T04 | P0 | 锁定软件工程报告，再要求安排另一项任务占用它的时段 | 不静默移动锁定任务；说明冲突，用户明确解锁后才能移动 |
| T05 | P0 | 新增“900分钟，明天12:00截止”的任务 | 不伪造成功，不静默遗漏其他任务；区分明确容量不足与搜索未找到方案 |
| T06 | P0 | 生成候选后点放弃，再刷新 | 正式任务和正式计划保持原样，聊天记录保留 |
| T07 | P0 | 连续点击发送、重复确认同一方案 | 不重复新增任务或重复应用计划；正式数据只改变一次 |
| T08 | P0 | 生成候选后，在任务管理页修改同一任务，再采用旧方案 | 拒绝旧候选，提示重新计算；不覆盖最新修改 |
| T09 | P0 | 模拟AI超时、网络失败或非法输出 | 中文说明问题，保留输入，不显示虚假的成功，不改正式数据 |
| T10 | P0 | 设置已逾期任务或已开始安排，再生成调整 | 提示逾期或进度核对；不改DDL、不向过去排新任务、不移动已开始安排 |
| T11 | P0 | 生成候选后推进时钟，使安排开始时间已过去，再确认 | 重新校验并拒绝失效方案；此项由后端测试控制时间，不改正常环境时钟 |
| T12 | P1 | 取消一项未来任务，再预览；另将已开始任务标记完成 | 未来取消任务显示移除；确认前不写正式状态；已开始历史保留 |
| T13 | P1 | 采用方案后停止、重启演示服务，不加Reset | 已保存任务、会话和方案能恢复 |
| T14 | P1 | 重复初始化或重复导入同一份课表 | 不增加重复课程；周次、单双周和连堂时间正确，歧义资料继续待核对 |
| T15 | P1 | 用非北京时间浏览器及320/390宽度查看页面 | 日期、DDL和课程仍按北京时间；窄屏可切换聊天与日程，关键操作可见 |

故障模拟、时钟推进、重复请求等由开发同学使用已有自动化测试完成；普通体验同学不需要改数据库或密钥。课表测试应对照本地原资料逐项核对，尤其检查周四14:00课程冲突案例。

## 六、邀请同学试用

建议邀请3–5名没有参与开发的同学，每人约10–15分钟。人数与时长是建议，不是已经完成的测试。

给他们三个任务，先不教具体按钮：

1. 添加一项明天截止的任务，并找到它的安排。
2. 修改时间，让它产生冲突，再解决冲突。
3. 判断哪些内容已经保存，哪些仍待确认，然后采用或放弃。

观察是否需要提示、是否理解DDL、是否看懂移动原因、是否分清候选与正式计划。最后问：“哪一步最困惑？”“这个调整是否有帮助，为什么？”“有没有你希望保留但被移动的安排？”

建议目标：至少80%的体验者能独立完成三项操作，并能正确说明确认前后区别。样本小，仅用来发现明显问题，不作为统计结论。

## 七、怎样记录和判断通过

每个案例使用以下记录表；涉及个人课表的截图只保留本地。

| 案例编号 | 日期/版本/模型 | 输入与操作 | 实际结果 | 通过/失败/未测 | 补充回答或重试次数 | 证据与问题 |
|---|---|---|---|---|---|---|
| 例：T01 | 待填写 | 待填写 | 待填写 | 未测 | 待填写 | 截图或日志路径 |

记录AI调用耗时、补充回答、重试以及失败类型。真实AI与模拟响应分开统计；重试成功不能抹掉第一次失败。修改代码后优先重测失败案例及受影响流程。

展示前的通过标准：

- 连续主流程可完成，所有P0案例通过，无课程覆盖、漏任务、DDL误改或未确认写入。
- 真实AI完成新增、补充信息、引用任务修改、紧急插入和再次调整；确认后刷新、重启能恢复。
- 每项日程变化可核对，所有失败有清楚反馈，并保护正式数据。
- 前端、后端和构建检查通过；P1问题有明确处理记录。

固定演示时间只用于验证流程，不代表真实日期下的性能或服务可用性。已出现网关超时，因此建议展示前用真实模型演练一次，并准备清楚标注的手动任务卡片备用流程；备用流程不算真实AI验收通过。

## 八、现有自动化测试如何复验

从项目目录执行：

```powershell
Set-Location backend
..\.venv\Scripts\python.exe -m pytest -q
Set-Location ..\frontend
npm.cmd test
npm.cmd run build
Set-Location ..
```

浏览器样例测试、真实模型流程、真实浏览器流程分别执行；每条独立测试前重置演示环境：

```powershell
& .\codex\启动演示版.ps1 -Reset -AiModel 'glm-5.3-flash'
.\.venv\Scripts\python.exe .\codex\browser_mvp_acceptance.py

& .\codex\启动演示版.ps1 -Reset -AiModel 'glm-5.3-flash'
.\.venv\Scripts\python.exe .\codex\real_browser_smoke.py
```

真实AI完整流程及模型记录方式见[MVP启动与演示](MVP启动与演示.md)。这些脚本会改变演示数据，测试后Reset恢复初始展示。

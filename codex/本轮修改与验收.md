# 本轮修改与验收

依据用户提供的《student-growth-assistant_本轮修改建议.md》，落实七项改动。保留规划、复盘、我的档案三页和现有模型接口；没有增加路由框架、SSE、多用户或长期周期任务系统。本轮代码尚未上传 GitHub。

## 逐项实现

| 建议 | 实际修改 | 验证重点 |
|---|---|---|
| 目标优先级 | 1、2、3 分别采用 3、2、1 权重，仅 active 目标参与；新候选立即读取目标资料 | 评分方向、无目标回退、新任务目标关联、反馈及复盘联动 |
| 策略独立 | 均衡 4/3/3、习惯 6/2/2、稳定 2/6/2；默认模式只选择方案 | 切换默认偏好不改策略权重；合适场景产生不同安排；相同安排去重 |
| 旧界面清理 | 移除未使用的 WeeklyPlan 页面及组件；旧纯函数移入 codex/legacy，后端旧接口保留 | 旧 API 契约与纯函数回归、前端构建 |
| 聚合读取 | Tasks 使用 dashboard，复盘和档案使用 context；执行历史按需展开 | 1、20、100 个任务时任务聚合 SQL 查询不超过 7 次，不逐任务调用接口 |
| 真实迁移 | Alembic 冻结基线、显式版本、结构校验、升级前备份；启动与 CLI 共用入口 | 空库、已知旧库、重复升级、未知结构拒绝且不标记成功 |
| 细粒度及拆分 | 5 分钟网格；默认连续，允许拆分后按最小分段及最大段数搜索 | 45/75/105 分钟、08:05 起点、跨日分段、总时长完整、锁定及已开始片段 |
| 两周安排 | 本周剩余时间和下周共同搜索；界面切换；一个事务保存两周 | 两周课程展开、跨周同一任务 ID、部分完成后仅安排剩余量、过期候选拒绝 |

## 使用方式

1. 规划中输入任务、具体 DDL 和所需分钟数；非 5 分钟倍数仍需修正。
2. 默认按连续任务处理。任务卡片可勾选“允许分段安排”，默认每段至少 30 分钟、最多 4 段；最后不足最小段的剩余量允许保留。
3. 通过“本周／下周”查看同一候选的两个周视图，切换不生成另一份计划。
4. 采用前任务与日程不变；采用时重新检查版本、当前时间和硬约束，并原子保存两周。
5. 已结束但未反馈的任务需核对剩余工作，不根据时间自动认定完成。部分完成记录保留实际发生时间，后续只安排已确认的剩余量。

## 验收证据

浏览器脚本 `revision_browser_acceptance.py` 已实际通过 15 项检查：本周／下周切换、日程完整高度、75 分钟手动卡片、拆分设置、确认前不写正式任务、采用后持久化、不刷新页面的任务列表同步、部分完成反馈、三页聚合、刷新恢复、390×844 窄屏、非北京时间浏览器、预览目标关联、两个分段标识及分段采用保存。浏览器运行时错误为 0。

真实 DeepSeek 验收脚本 `revision_ai_acceptance.py` 使用独立匿名库，完成两轮理解与推荐：180 分钟任务拆成下周两段；随后确认部分完成，再把同一任务的剩余 120 分钟调整为连续时段。两轮运行均 completed、无错误码。检查了真实解析、真实推荐、确认前不写正式任务、继续对话、剩余量与跨周保存。这些是实际外部调用，不是模拟响应。

完整后端回归 526 项通过，耗时 305.38 秒；前端 56 项测试通过，生产构建通过。后端只有 Starlette/httpx 兼容弃用提示，没有失败测试。后端测试按 README 从 `backend` 目录执行；在根目录运行时，两个旧子进程导入测试会因找不到 `app` 失败，标准目录下已整套重验通过。原始日志、数据库和浏览器截图只保存在忽略的本地目录中，避免公开个人信息。

本机代表性纯排程测量（含三策略搜索，不含 AI 网络等待）：3 个 75 分钟任务为 0.735 秒，6 个为 4.438 秒，均生成完整合法方案。无偏好冲突时去重后只有一个方案。这是小规模样例，不作为 100 个任务或复杂约束的性能保证。

## 修复的联动问题与边界

主要实现文件：`assistant_scheduler.py`（权重、网格、分段与校验）、`assistant_state.py`（两周任务集合与剩余工作）、`routers/assistant.py`（原子确认）、`routers/dashboard.py`（聚合读取）、`schema_migrations.py` 与 `codex/migrations`（迁移）、`AssistantPage.jsx` 与 `TasksPage.jsx`（周切换、拆分卡片、执行联动）。对应回归测试集中于 `test_revision_schedule.py`、`test_revision_workflow.py` 和 `test_revision_migrations_dashboard.py`。

- 新候选原先未即时附带目标优先级，现已在预览时补齐，避免等保存后才影响排序。
- 手动计算释放数据库写事务后再执行搜索，发布候选前重新检查版本，避免长搜索锁住其他修改。
- 原先每个连续任务都尝试分段，导致不必要延迟；现在优先连续，仅在需要时枚举有限分段。
- 已采用任务与执行反馈会刷新规划和任务抽屉，避免等待用户整页刷新。
- 过去的候选不能借“已经开始”豁免校验；正式已开始片段保持原位，未采用且进入过去的方案拒绝确认。

搜索仍是确定性有界搜索：每层最多 64 个状态，每策略最多 50,000 次扩展，并设置搜索时间上限。拆分不是所有组合的穷举；未找到方案不能宣称数学上无解，也不保证全局最优。候选可能少于三个，不能用相同安排冒充不同方案。

复杂的目标关联、已有任务和分段限制组合，在浏览器补验中曾超过测试客户端原先的 20 秒等待限制。将测试端等待设置为现有接口的 125 秒后，完整流程通过；这不代表复杂组合都能即时返回。正式 AI 运行仍使用真实阶段、取消和原有整轮上限，不伪造完成进度。

执行学习的缩时建议仍使用原有保守统计及 30 分钟向上取整规则；本轮 5 分钟网格改变的是任务输入与日程安排，不降低学习证据门槛，也不通过缩短估时伪造可行方案。日程仍不安排两周范围以外的任务，不自行延长 DDL。

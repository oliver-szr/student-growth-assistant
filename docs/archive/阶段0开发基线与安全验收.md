## 根因与复现

旧 `/api/plans/candidates` 直接调用只接收周、任务和时间规则的单周引擎，缺少当前时刻与任务排程资料。`/confirm` 原先只检查候选状态和全局版本，不重新校验保存片段。因此时钟推进、锁定资料被忽略或候选快照损坏时，版本相等仍可能接受非法结果。

新增 `test_plan_safety.py` 最初 19 项在修复前全部失败，复现了：过去时间排程、结束周仍生成、时钟推进后确认、遗漏锁定任务、覆盖开始/历史记录，以及非法持久化片段被接受。测试使用固定时钟及每例独立数据库，不连接正常数据库。

Assistant 另有两处确认防御缺口：保留历史可从待确认候选派生，未再次证明其对应正式快照；重复声明已有锁定可能替换校验基线。通过隔离测试直接改变已保存候选来检验最终校验边界，两项修复前均错误返回 200。该复现不表示普通前端提供了任意修改候选 payload 的接口。

## API 与修复后行为

没有新增路由；请求和成功响应结构保持原样。

- 旧单周候选：临时占用已过去的工作时间，下一合法起点按 5 分钟网格选择；临时规则不存库，不改变 DDL。
- 旧 API 的单周算法无法安全表达锁定、分段、固定开始、限定时段，或同周已有已开始/历史片段时，返回 `422 PLAN_REQUIRES_ASSISTANT`，引导现有规划工作台。结束周返回 `422 PAST_PLANNING_WINDOW`。
- 旧候选确认：重新读取任务、课程、保护时间、排程资料及正式记录，对持久化片段运行独立 Validator，检查完整性、唯一性、时长、网格、DDL、冲突及当前时间；另外比较课程快照。失败仍为 `409 STALE_CANDIDATE`，可附 `reason_code`。
- Assistant：保留的记录必须对应正式快照，不能遗漏已结束正式片段或增加伪历史；已有锁定仍以正式时段作为校验基线。显式解除锁定的现有操作保持可用。
- 旧接口重复确认继续返回 `PLAN_NOT_CANDIDATE`；Assistant 已采用方案继续幂等返回。两者不重复写入或错误推进版本。
- 所有拒绝均发生在正式替换前；异常统一回滚，不产生半份日程、孤立任务或错误 revision。保留原同周唯一正式计划约束。
- AI 继续只产生草案。无 AI Key 时，手动录入与程序排程可使用；日程结束、计时结束均不会自动完成任务。

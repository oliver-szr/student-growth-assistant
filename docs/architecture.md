# 个人成长助手：现行架构

## 现行三页工作台（2026-10）

React 的 `App` 提供规划、复盘、我的档案三个入口；复盘和档案复用 `WorkspaceChat`，规划保留周日程、任务抽屉和候选比较。页面显示采用北京时间，数据库身份隔离浏览器会话缓存。

FastAPI 将 HTTP 校验交给 routers，排程、业务事务、统计和模型接入交给 services。SQLite 保存任务、课程、目标版本、偏好规则、执行反馈、对话、后台运行和修改草案；显式迁移和备份支持已有数据升级。

规划会话按周组织，复盘按选定周组织，档案跨周保留。AI 返回结构化意图，程序校验引用与字段，草案只写候选数据。用户确认时检查来源版本，在事务内应用相关修改；正式修改使旧候选失效。

助手排程覆盖本周剩余时间与下周，使用 5 分钟网格，优先连续安排，明确允许后才尝试有限分段。均衡、习惯、稳定使用各自固定权重；默认偏好只选择方案，不改写三种策略。目标优先级 1 高于 2、3，仅生效目标参与评分。独立校验完整时长、课程、保护时间、DDL、锁定和过去时间；确认在一个事务内替换两周计划。基础 `scheduler.py` 保留单周连续安排的旧接口兼容。

任务、复盘、档案通过聚合接口读取，执行记录按需加载。启动和命令行共用 Alembic 升级入口，旧库结构检查通过后才迁移；不盲目标记版本。旧 WeeklyPlan 页面已移除，相关纯函数移入 `frontend/tests/fixtures` 供兼容测试。当前规则与实际验收见 [阶段 1 验收](archive/阶段1局部重规划与冲突解释验收.md)。

个人偏好采用稳定类别标识和可编辑规则；软偏好不解除硬约束。执行反馈保存历史快照，统计先由程序计算，再交由 AI 组织解释；未经确认的观察不能自动变为长期习惯。

匿名演示由 `scripts/demo_scenario.json` 定义。正常时钟与数据库不因演示启动改变，私有课程只能显式导入。更多目录见[README](../README.md) 的目录说明。

阶段 0 在现有路由外增加小型 `plan_safety.py`：旧单周 API 使用临时占用阻止过去时间安排，继续复用原 Scheduler 和独立 Validator，确认时重新校验当前数据和课程快照。无法表达的硬时间资料、分段或已开始记录明确拒绝，不覆盖旧正式计划。Assistant 继续使用两周校验器，另核对保留记录确实来自正式历史；已有锁定不能借候选中的重复锁定声明移动。两条路径均保留版本检查和原子确认，无新增表或迁移。

### 阶段 1：局部调整范围

`assistant_state.proposed_world` 同时保留正式两周快照与待确认候选上下文。`scoped_replanning` 根据任务 ref、正式片段全集、当前任务资料、真实规则和本轮动作分类；未受影响且合法的未来任务仅在排程输入的深拷贝中临时冻结，历史与既有保护继续由原机制维护。正式任务的锁定资料不会被临时冻结写回。

仍调用原 `assistant_scheduler.arrange`，保持三种策略权重 `(4,3,3)`、`(6,2,2)`、`(2,6,2)`。策略只在授权范围内评分；偏好或 AI 临时规则不授予扩大范围权限。移动任务数、片段数、配对时间位移和重叠比为观测指标，没有加入新的隐藏权重。

局部失败返回空 items、待处理任务和程序诊断。仅在普通搜索未找到完整方案且有可放开的合法任务时，提供明确的扩大范围操作；搜索预算耗尽单独解释，不声称绝对无解。扩大后仍冻结已开始/锁定的任务。授权来源保存在现有候选 JSON，同一版本草案链可继承，采用、放弃或版本变化后重新从局部开始。

现有 AssistantMessage.content 记录范围摘要校验值，防止候选范围元数据损坏或被移除后退回旧行为。确认时核对标记、来源候选、正式快照摘要，并按当前数据重新分类和校验冻结片段，随后继续阶段 0 的历史核对、完整约束校验和两周原子事务。此标记是数据库内部一致性检查，不能防御同时任意改写数据库多个表的攻击者。

结构化变化与诊断附加到候选 payload；前端 `ScopedChanges` 复用原工作台、周日历和确认流程。没有新增表、迁移、Provider、框架或依赖。JSON 备份自动包含新增元数据；恢复继续使旧候选失效。详细机制和验证见 [阶段 1 验收](archive/阶段1局部重规划与冲突解释验收.md)。

## 分层与运行工具

页面统一通过 frontend/src/api.js 请求；routers 负责 HTTP，services 负责业务，models/schemas 负责数据与契约。排程核心不直接调用模型，等待 Provider 时释放数据库事务；正式修改在版本校验和 SQLite 写事务内完成。所有时间边界使用北京时间，SQLite 时间戳保持 UTC。

旧 `/api/plans` 单周兼容入口继续存在，有独立的安全拒绝与确认复验；当前规划工作台使用 `/api/assistant` 两周候选流程。旧单周 API 的前端纯函数只作为 tests/fixtures 中的兼容测试辅助，不重新挂载旧页面。

Alembic 资源位于 `backend/alembic/`；`scripts/migrate.py` 与启动共用 schema_migrations.upgrade_database，不重新生成基线。阶段 2 新增 `0002_task_hierarchy` 和 JSON v2；旧 v1 先经冻结契约校验，再显式补齐普通任务默认值。数据库与迁移说明见 [database.md](database.md)。

脚本、约束、演示场景的当前布局见 README。新演示和审计产物进入 scripts/.runtime、scripts/.local；原本地目录不移动。演示路径白名单保留旧库兼容；备份若已存在旧默认目录继续使用，其他安装默认用 scripts/.runtime/backups，显式 SGA_BACKUP_DIR 仍优先。没有受版本管理的运行工具依赖旧目录。

GitHub Actions 在 PR/main 更新时运行后端全套 pytest、依赖/文件引用检查，以及前端锁定安装、测试与构建。本地正式测试保留在 backend/tests 和 frontend/tests，测试默认固定应用与记录时间，单例仍可覆盖时钟，数据库放在 pytest 的隔离临时目录。可选浏览器、压力基准和真实模型 smoke 不属于自动核心测试或启动流程。具体 API 见 [api-contract.md](api-contract.md)，阶段验收记录位于 docs/archive。

## 阶段 2：任务拆解与两级层级

继续使用 `Task`，增加 `parent_task_id`、`task_kind`、`sort_order`。父容器的 duration_minutes 保留原始预期用于比较；它的 status 保持 todo，真实进度由子任务汇总。task_hierarchy 统一验证父引用、两级上限、DDL、转换与备份规则；已有任何计划引用、反馈、计时或锁定的可执行任务不能直接转换类型。保留无硬删除接口的策略，父容器也不能以批量取消静默处理子任务。

拆解复用 `GrowthChangeDraft`（scope=task_breakdown）、`AssistantSession` 与消息 JSON，没有新增草案表。现有 assistant_ai/claude_client 返回强类型建议；模型调用前后分别取版本快照，等待期间释放事务。AI 不能改写用户给定父 DDL。用户可以编辑父 DDL，但确认前仍会校验全部子任务与当前时间。

草案 payload 保存输入、结构化内容、编辑 version 与确认后的任务 ID。生成请求可按 client_request_id 重试；编辑/确认检查草案 version 与全局 source_revision。`BEGIN IMMEDIATE` 串行化确认：父任务、全部子任务、目标上下文、applied 状态和 planning revision 一起提交。重试已确认草案返回原 ID；并发确认不会生成第二棵树。确认草案不写日历，之后仍走原候选→独立校验→用户采用流程。

前端 `TaskBreakdown` 在规划页提供 AI/手动入口；合法编辑暂停 1.2 秒后自动保存，也能显式保存。无效或网络失败保留当前编辑并提示修正/重试，刷新可从服务器读取已保存草案。`TaskHierarchy` 在原任务与执行区展示可折叠子任务、完成数、初始估时总量和剩余量；复用 TaskForm、api.js 与既有 CSS。

task_library、attention 和两条排程确认边界仅接受可执行任务。子任务沿用原两周、5 分钟网格、分段、局部范围、历史和锁定机制。反馈/计时也拒绝父容器，因此成长统计只收到子任务的正式执行事实。完成比例为 done 子任务数 / 全部子任务数（含 cancelled，另列取消数）；总预计为子任务初始估时之和，剩余只加总 todo 的当前分钟，实际投入只加总未撤回的用户反馈。已安排只表示正式计划中有记录，不等于已执行或完成。目标按创建时继承，之后独立管理；父容器不贡献一次额外完成量。

## 阶段 3：只读成长统计

`growth_statistics` 路由提供一个有界聚合接口，`analytics_schemas` 严格定义响应，服务在 SQLite 显式只读快照事务中汇总，结束后 rollback。最多 7 次 SELECT，不逐任务查库；加载任务/目标/类别元数据、范围反馈和正式片段，仅对完成配对任务批量补读范围外反馈。没有统计持久化表、缓存、后台同步、AI 请求或写入初始化助手。

沿用北京时间、周一开始及固定时钟。完成按有效 completed 反馈的 completed_at 归周，旧记录回退 occurred_at 并标记；投入按 occurred_at 归周。撤回记录排除，同 Task ID 的完成去重；当前 status 不反推历史。父容器同时从反馈和计划统计排除。实际投入只采用反馈 actual_minutes，不再加计时器；无反馈或缺耗时输出 null，已知小计、缺失条数与合法历史零值单列。

类别使用反馈的稳定标识快照，名称按当前类别（含停用）或历史名称展示，无快照归未分类。估时配对比较完成反馈的原始估时与截至完成的全部有效投入，包含范围外的早期部分完成；沿 supersedes_id 定位原始记录顺序，晚补更正替换原事实。耗时不全、估时不一致或不可解释更正链排除；至少 3 项才描述类别观察，不作效率/未来预测。

目标汇总复用 growth_tracking 提取的 goal_progress_from_feedback：time 取反馈分钟，count/deliverable 取不同完成 Task ID。最新周进展对照当前目标值，当前关联任务状态单列。新生成的周复盘共用有效反馈与完成归周逻辑，旧复盘版本继续保留生成时事实；修复默认反馈时间捕获函数别名的问题，使其跟随统一固定时钟。

Review 原结果区挂载 GrowthAnalytics，api.js 统一请求；原生 SVG、CSS 和可访问表格提供 4/8/12 周、刷新、错误重试、空数据、未知耗时和样本不足状态，无新增图表依赖。移动端继续复用聊天/结果切换，图表与表格在自身容器横向滚动。保存的周复盘和待确认建议保留。缺少不可变周初任务集和取消事件日志，因此不计算历史完成率和周取消数；当前正式快照也不能代表当时的计划版本。详细结果见 [阶段 3 验收](archive/阶段3成长统计与可视化验收.md)。

## 阶段 4：性能与可重复验证

先在1c5b2cb建立固定输入基准，再使用cProfile确认热点。beam扩展时，同一完整状态原先在分支与全局排序中分别评分；现在将评分与状态一起保留，第二次排序复用原值。两次稳定排序的键与插入顺序不变，不增加持久化缓存，不改5分钟网格、两周窗口、分段规则或三策略权重。独立Validator、范围授权和确认事务均保持原路径。

每策略20秒、50,000次扩展及64状态保留原阈值，SEARCH_LIMIT另外报告budget_kind=time/expansions、expansions及phase=search。候选预生成和分段内部仍是粗粒度时间检查，非抢占式硬超时；所有手动压力基准额外使用子进程超时，不将终止当成功日程。基准脚本不访问数据库/模型，普通规模重复3次，100任务压力只运行1次。7个阶段3小场景输出指纹进入轻量回归，重负载不进入CI。

scripts/integration_demo.py是显式独立工具：--serve新建白名单目录内UUID演示库，仅在该进程Mock拆解并禁止真实模型；正常app.main不导入该工具。--verify在空匿名库上执行草案编辑、幂等创建、子任务排程、课程冲突局部修复、反馈、父进度和统计的HTTP链路。浏览器验证与HTTP/Mock结果分别记录，见 [阶段4报告](archive/阶段4性能与工程质量验收.md)。
